# Creative Department Instructions

Follow `11-SYSTEM/OPERATING-SYSTEM.md` first. Read `DEPARTMENT.md`, only the creative skills relevant to the task, applicable approved brand guidance, and task-relevant product, goal, project, and reference context.

## Working rules

- Separate exploration from approval. Label concepts and variants as proposed until a person chooses them.
- Do not invent brand rules to fill gaps. Use neutral, clearly provisional choices and state what is missing.
- Preserve editability and source files when practical; distinguish source, working, approved, and output assets.
- Validate hierarchy, readability, accessibility, responsiveness, and content fit before calling work complete.
- Explain any durable design-system choice that could affect future work and seek approval before treating it as a standard.
- Use an official general skill only when its real `SKILL.md` exists. A marker or `SKILL.template.md` is not active guidance.

Brand-specific skills are company-owned. Do not replace their guidance during a framework update. If they conflict with current `03-BRAND` records, report the conflict and ask a human which should be canonical.

## Brand-specific skill routing

Before starting branded creative execution, identify the relevant medium and check whether its folder in `skills/brand-specific/` contains an active `SKILL.md`. A `SKILL.template.md` alone means the skill has not been created.

When the task would materially benefit from a missing brand-specific skill, recommend creating that skill first. Use `workflows/build-core-brand.md` when the missing need is cross-medium core brand direction; use `workflows/build-brand-skill.md` for `web-design`, `social-media`, `presentation`, `print-editorial`, or `motion`. Briefly explain that the skill turns approved brand evidence, examples, dislikes, and preferences into repeatable execution guidance and should improve the quality and consistency of this task and future work. Also point out that the first version is a starting point: test it on representative work, give specific feedback tied to the outputs, and use `workflows/refine-brand-skill.md` to improve it. Better feedback and repeated testing should lead to better-quality results.

Make the recommendation before substantial execution, but do not present the skill as mandatory. If the user chooses to continue without it, use the available canonical brand context, state important gaps or provisional choices, and proceed within the requested scope. If an active skill exists, load it and use it with the relevant general skill.

Use `workflows/build-brand-skill.md` to create a skill and `workflows/refine-brand-skill.md` to change one. Casual feedback is evidence, not permission to modify an approved skill.
